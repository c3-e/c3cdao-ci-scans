01

Current and previous contracts

Current

The gate executes the plan

docker buildx bake --print produces the reviewed plan. The gate executes the same targets with the same input, environment, tags, and base-image overrides.

Derived contract

Compose and Helm supply the contract

Compose defines build images and digest-pinned runtime dependencies. The rendered chart defines deployment, readiness, and the HTTP smoke target. Lint blocks ambiguous projects before build.

Run record

GitHub retains the review artifacts

The run publishes the normalized plan, scan-set diff, SBOMs, scanner reports, job summaries, and the required Security Gate verdict.

v0.5.x

Consumer-owned execution

A consumer-owned Makefile.ci emitted a JSON manifest and implemented build, security-context, and smoke prerequisite targets. The gate verified outputs after those scripts ran. Removed at v0.6.

Positional

Primary plus secondary images

scan_image named the primary image. Remaining manifest entries carried separate artifact names and implicit local tags. Replaced by equal matrix legs.

Run-local

Run-local evidence

The current workflow stores plans, images, SBOMs, and reports as independent job outputs and Actions artifacts.

02

Execution architecture

Committed files feed one derivation. Build fans out per image; smoke and scans share its artifacts; one check aggregates.

One file per concern

1

App code

Reads its resources from the environment, such as DATABASE_URL. It never knows who provided the database: a Compose container on a laptop, a pod in the smoke cluster, or a managed service in production.

2

Compose holds build truth

The one place that says which images this repository produces (build:) and which it merely downloads (x-downloaded-dependency). Local development runs this file daily, so it cannot silently rot.

3

The chart holds runtime truth

The one place that says how images run: readiness, Services, environment wiring from Secrets. Standard Kubernetes fields only. CI reads the chart and never extends it.

4

The caller is a pointer

Data, never behavior: which Compose file, which chart, which smoke resources, pinned to which gate revision. The last cross-repository surface, and it is declarative.

i
Build and scan remain separate jobs

GitHub Actions resolves dependencies at job boundaries. A combined job would delay cluster smoke until vulnerability scanning finishes. Separate jobs let smoke and image scanning consume the same build artifacts at the same time.

03

Consumer contract

Onboarding documentation states these conventions; caller lint enforces them.

Compose

Build services are explicit

Each non-local build: service supplies an image: tag and healthcheck:. A downloaded dependency declares its role, immutable digest, and chart-facing tag.

Dockerfile

Build inputs stay explicit

Build args use literal mapping values. The gate neither supplies nor overrides any build arg; base images are the Dockerfile's own choice, and every build targets linux/amd64. Caller lint rejects host pass-through, build secrets, and SSH in v1. Each leg's Bake execution also uses a per-target GitHub Actions cache scope for layer reuse across runs.

Helm

Runtime intent stays in the chart

Deployable workloads define readiness. Exactly one Service-backed HTTP readiness target supplies the post-deploy smoke request.

Caller

The request stays thin

The caller selects Compose/chart paths, release, namespace, image_only, and gate-owned smoke resources. It maps four registry secrets explicitly.

docker-compose.yml conforming build service 
services:
  api:
    image: app-api:ci
    build:

        APP_PATH: apps/api

  postgres:
    image: pgvector/pgvector@sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
    x-downloaded-dependency:

Ship-set invariant S \ D ⊆ B
S
Images scheduled by the rendered local chart
B
Tags produced by non-local Compose build services
D
Declared digest-pinned runtime dependencies

The gate builds and scans every application image. Downloaded dependencies such as PostgreSQL support smoke but are not release artifacts. A scheduled image outside B and D blocks.

One URL, three database providers

Local dev

Compose provides it

A digest-pinned pgvector container beside the app. Tests and data ingestion point DATABASE_URL at it.

CI smoke

The gate provides it

A gate-owned module stands up the same database in the smoke cluster before the chart installs and publishes the connection URL as a Secret.

Production

The platform provides it

A managed database service; operations create the same Secret from its endpoint. The application code is identical in all three environments.

04

Preserved security coverage

The redesign moves build and smoke logic into the gate while preserving scan coverage and enforcement.

Job Coverage Posture
secrets-scan TruffleHog verified-secret scan Ramp controlled
sast-semgrep Semgrep source analysis Warn-only
sast-sonarqube Ephemeral SonarQube analysis Warn-only
helm-check Helm lint/template + restricted PSS Blocking
image-scan × N Trivy + Grype image and SBOM scans Ramp controlled
cluster-smoke kind deployment, readiness, HTTP probe Ramp controlled

Enforcement ramp

SECURITY_SCAN_BLOCKING keeps vulnerability findings and smoke failures advisory during onboarding, then makes them blocking after the canary produces stable signal. Skipped, cancelled, and infrastructure-failed blocking jobs still fail the aggregate gate.

Hardened bases

The gate handles Chainguard and Iron Bank authentication and failover. Base images are the consumer Dockerfile's own choice; the gate scans each image as built.

i
OpenVEX is the only sanctioned suppression path

A committed .trivyignore or .grype.yaml with any real entry blocks (suppression-format); disposing a finding requires a statement in .openvex/templates/main.openvex.json carrying a status and justification. The gate publishes each build's image to a job-local registry so Grype resolves a real, digest-backed product identity to match VEX statements against.

05

Run records

Every run keeps the GitHub Actions summary and artifact model, plus one consolidated bundle.

1

Plan

Publish the normalized Bake plan and scan-set diff.

2

Build

Publish image archives and SBOMs for each matrix leg.

3

Scan

Publish scanner reports, the applied OpenVEX document, and a per-service security-export bundle.

4

Aggregate

Evaluate job results through the required Security Gate check.

i
One consolidated download, one PR comment

export-bundle re-packages every per-service export, the source SBOM, and the plan BOM into one security-export-full-<short-sha> artifact, then posts (or updates) a PR comment summarizing each service's Trivy/Grype High+Critical counts, VEX source, and any pending disposition. Convenience only: it runs if: always() and never appears in the Security Gate's needs:, so it can never affect the required check.

Follow-up

Signed durable evidence

  • Requires an approved signing identity and verification policy
  • Requires an approved evidence repository and retention policy
  • Requires a compliance need beyond existing Actions records
06

Sibling workflows

Two more reusable workflows serve the same consumers. Neither is the scan gate; neither is folded into it.

Merge-only · registry writes

publish-staging-chart.yml

Packages a merged PR's Helm chart, and optionally its images, to a staging OCI registry: charts-staging/<pilot> and images-staging/<pilot>/<image>, tagged 0.0.0-mech.<pr>.<sha>. Triggers only on a merged pull_request close; an open PR's ordinary pushes produce nothing. The one workflow in this repo that writes to a registry outside a same-run build.

Caller-triggered · read-only

composed-smoke.yml

Pulls N pilots' already-published staging artifacts and installs them together in one kind cluster, health-checking each pilot's own rendered Service. Proves cross-pilot composition that a single pilot's own gate run can never see. Reuses the gate's own smoke-catalog modules (postgres-pgvector, gateway-crds) rather than a second copy.

i
Why three workflows, not one

Different trigger models (every push vs. merge-only vs. caller-chosen) and different side-effect profiles (read-only scan vs. registry write vs. read-only cross-pilot install) argue against folding any pair together. Full contracts: PUBLISH-STAGING-CHART.md and COMPOSED-SMOKE.md.

07

Rollout and proof

The major release removes Makefile.ci and moves consumers to the derived contract.

  1. 01

    Prove Bake semantics

    Verify profiles, ARG precedence, scrubbed environment behavior, tags, and N-image plans.

  2. 02

    Implement on a branch

    Add derivation, lint, resource catalog, separated jobs, and run-record publication.

  3. 03

    Run a consumer canary

    Point a representative consumer's canary branch at the redesign. Compare baseline and redesign runs for the same commit: jobs, targets, artifacts, findings, posture, and final verdict.

  4. 04

    Exercise the chart path

    An image_only canary cannot exercise Helm or cluster smoke. Use a chart-owning consumer to verify ship-set, readiness, resource-catalog, and cluster-smoke behavior.

  5. 05

    Publish the major version

    Pin consumers to the immutable workflow revision and retain the stable required-check context.
